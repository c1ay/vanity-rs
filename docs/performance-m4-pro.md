# M4 Pro：Metal 后端验证与性能

测试日期：2026-08-28。设备为 Apple M4 Pro，10 个性能核心、4 个能效核心、20 核 GPU。

**当前默认 batch 262144、16-bit 窗口、融合分块求逆、双在途命令及最新验收见[窗口位宽与拆核融合](#窗口位宽与拆核融合2026-08-28第四轮测量)。前几节保留首次接入、批次补测、流水线和 8-bit 结构优化的历史记录。**

## 测量方法

- Release 构建，使用项目默认优化选项；未额外启用 `target-cpu=native`、LTO 或修改 C 库编译参数。
- CPU 基线是本次接入前已经升级到 secp256k1 0.31.1 的版本，不是最初的旧版依赖。
- 首次验收每组预热 3 秒，测量三轮，每轮至少 30 秒。CPU 使用 1/10/14 线程；GPU 批大小为 1024/4096/16384。更大批次的后续对照见文末「批大小补测」。
- 采用持续计时并在停止后等待所有线程或 GPU 批次完成，计数包含实际完成的尾批。没有给每个 CPU 线程分配相等固定工作量，以免性能核、能效核的等待时间扭曲吞吐。
- 两侧均包含 CSPRNG 私钥生成、地址推导、匹配、最佳候选判断、计数和原子快照保存。Metal 还包含每批抽样复核和候选复核。测试条件为 40 位零前缀。
- 基准排除终端绘制；CPU 基线在保存的旧源文件中加入同等计时脚手架，当前版本调用生产搜索循环。因此这是搜索路径的持续基准，不是未修改 CLI 的整体墙钟计时。
- `stop_sec` 包含停止请求后的线程/GPU 收尾和最后一次快照保存；初始化另计。Metal 驱动编译缓存未清理，初始化时间不能代表完全冷启动。
- CPU 核心未绑定，系统后台负载、调度和温度会带来波动。各组串行运行，测试期间不并行编译或运行其他基准。

原始逐轮计数、耗时、日志、源文件哈希、旧版源文件及基准可执行文件保存在本地 `target/gpu-verification/`。该目录被 Git 忽略；测试生成的候选私钥只存在于自动删除的临时目录，不写入性能报告。

## 正确性与回归范围

- 原有 19 项单元测试保留；增加后端选择、参数、批次计数、错误传播、取消和错误候选拒绝测试。
- 真正执行 Metal 的差分测试比较模加、模减、模乘、平方和求逆与 CPU 大整数参考值。
- 公钥和地址逐项与 libsecp256k1/tiny-keccak 比较，覆盖 `n−1`、所有单比特私钥、固定种子随机样本，以及 0/1/31/32/33/127/128/129/4095/4096/10000/65536 项批次。
- 生产 CLI 的 GPU 验证覆盖批大小 1/33/4096/65536、`auto` 默认选择、JSON 追加、TXT 输出、文件权限、私钥不进入默认日志和快照写入失败后的及时退出。

验证通过代表这些测试场景中结果正确，不代表完成了独立密码学或侧信道安全审计。

最终复检：Debug/Release 各通过 26 项单元测试和 1 项 CPU CLI 测试；两个硬件测试均显式执行并通过。`cargo build`、Clippy 全目标零警告、格式检查、CLI 帮助及 Git 空白检查也通过。详细输出在 `target/gpu-verification/final-checks.json`。

性能数据来自冻结的基准可执行文件。之后仅补充了主控异常退出时的取消保护、上传缓冲区错误退出清理测试及接口注释，未修改搜索计算热路径。

## 批大小补测

同日补测 16384、32768、65536，使用首次验收冻结的同一份 Release 基准可执行文件，未修改搜索计算。三个配置串行交错执行，每个配置各测三轮，每轮在独立进程初始化、预热 3 秒后测量至少 30 秒。顺序为 `16384 → 32768 → 65536`、`65536 → 16384 → 32768`、`32768 → 65536 → 16384`，降低固定顺序对结果的影响。

计数仍包含随机私钥生成、GPU 地址推导、CPU 匹配及复核、原子快照和已完成尾批。逐轮日志、计数、初始化耗时、运行顺序及可执行文件哈希保存在 `target/gpu-verification/large-batches-20260828-075656/`；运行脚本为 `target/gpu-verification/benchmark_large_batches.py`。以下为三轮中位数，百分比使用本轮重新测量的 16384 对照。

| 每批地址数 | 地址/秒 | 相对本轮 16384 | 逐轮吞吐范围（地址/秒） | 停止收尾中位数 |
|---:|---:|---:|---:|---:|
| 16,384 | 2,636,623 | — | 2,574,076–2,686,035 | 11.72 ms |
| 32,768 | 2,747,039 | +4.19% | 2,746,930–2,763,749 | 14.82 ms |
| 65,536 | 2,939,599 | +11.49% | 2,932,798–2,942,261 | 20.12 ms |

**在正式支持的范围内，推荐 M4 Pro 长时间搜索使用 65536。** 它是该轮已测配置中吞吐最高的，比 16384 快约 11.5%，比 32768 快约 7.0%。对照此前测得的接入后 14 线程 CPU，为约 2.34 倍吞吐；CPU 本轮没有重测，这个倍数属于跨轮次比较。

如果更重视较短的批次和停止响应，16384 仍是合理选择。65536 的三次停止收尾为 7.37–21.22 ms；这些是包含线程退出和快照保存的观测值，不代表纯 GPU 执行时间，也不是最坏情况保证。

批大小从 16384 增至 65536 是四倍，吞吐只增加约 11.5%，说明不能按批大小线性推算速度。每批固定提交、等待和抽样复核开销可以分摊，但逐项随机数生成、地址计算和匹配仍需执行。正式程序的上限仍为 65536；更大批次另外在临时副本中验证，见下一节。

本次更新使用建议和性能记录，CLI 默认值仍按原计划保留为 4096。测试没有改变随机数来源、匹配或校验策略。

## 超过 65536 的临时扩展实验

同日将当前源码复制到 `target/gpu-verification/extended-batches-20260828/source/`，仅在这个临时副本中将 Metal 后端和搜索循环的容量检查放宽至 262144，并扩展差分测试批次。没有改动 MSL 内核、私钥生成、匹配或校验流程，也没有改动正式源码或 CLI 的默认值、上限。

临时 Release 构建先通过 26 项普通测试，再实际执行 Metal 差分测试：保留有限域对照，逐项比较公钥和地址，批大小覆盖 0/1/31/32/33/127/128/129/4095/4096/10000/65536/65537/131072/131073/262143/262144，并验证私钥缓冲区清理及错误路径。最大批次包含 262144 个已知、单比特及固定种子随机私钥。这不等于独立密码学安全审计，也不代表已完成放宽正式 CLI 上限的验收。

使用同一份临时可执行文件重测 65536 作为对照，与 131072、262144 串行交错运行。每档三轮、每轮独立初始化并预热 3 秒后测量至少 30 秒，顺序为 `65536 → 131072 → 262144`、`262144 → 65536 → 131072`、`131072 → 262144 → 65536`。有效吞吐的计算范围与前述搜索基准一致。

| 每批地址数 | 地址/秒（中位数） | 相对本轮 65536 | 逐轮吞吐范围（地址/秒） | 停止收尾中位数 |
|---:|---:|---:|---:|---:|
| 65,536 | 2,924,857 | — | 2,920,271–2,941,400 | 17.05 ms |
| 131,072 | 3,045,115 | +4.11% | 3,041,235–3,050,460 | 34.25 ms |
| 262,144 | 3,105,866 | +6.19% | 3,105,667–3,106,084 | 37.40 ms |

结论：65536 是程序原定上限，不是这台 GPU 的硬件上限。临时实验中更大批次仍能提速，但收益递减：131072 到 262144 再翻倍只增加约 2.0%，65536 到 262144 增大四倍只增加约 6.2%。262144 是目前实测吞吐最高的配置，但正式 CLI 仍只接受最大 65536。超过 262144 的批次尚未测量，不能断言继续增大会有收益。

三个配置的停止收尾最大观测值分别为 24.17/39.34/39.33 ms；仍包括线程退出及快照保存，不代表纯 GPU 时间或最坏情况。后台负载、调度和温度的限制与前述测试相同。

临时源码、相对正式源码的差异、两份源码哈希和冻结的测试程序在 `target/gpu-verification/extended-batches-20260828/`；运行脚本为其中的 `run.py`。逐轮日志、原始 JSON、测试结果、程序哈希及核对记录在 `results-20260828-080547/` 子目录。已核对九轮均达到 30 秒、计数均为整批、吞吐与计数/耗时一致，且正式源码哈希未改变。

## 分阶段优化（2026-08-28，第二轮实施）

本节记录后续优化；上文的默认值、上限和推荐值属于历史验收记录。当前配置以 README 和本节最终结果为准。

### 实验与选择方法

源码、Cargo.lock、默认 Release 参数、原程序和仅放宽容量的基线分别冻结到 `target/gpu-optimization/20260828-m4-stages/`。本轮没有升级依赖、调整 LTO 或 CPU 指令集。所有性能程序串行运行，每次预热 3 秒；持续对照每档三轮、每轮至少 30 秒，波动超过 5% 的实验扩至五轮。正式保留门槛为中位收益至少 3%、至少两轮优于配对基线；波动仍大于 5% 的实验不启用。

正式吞吐测量关闭分段计时，包含 CSPRNG、地址计算、匹配复核和原子快照，排除终端绘制。初始化和停止收尾另列。GPU 执行时间另用诊断构建记录，不以 CPU 等待时间替代，也不把重叠阶段相加当作墙钟时间。

线程组和流水线均以 batch 65536 为固定对照，各三轮。流水线三轮均胜出，吞吐范围 3,453,844–3,479,711，波动 0.75%；原配置波动 0.53%。线程组保持原来的能力适配策略，在本机为 128；没有加入启动时自动调优。

专用平方、平方与快速模加法组合，以及显式展开循环的版本均通过真实 GPU 差分测试，但在预热后的 5 秒初筛中约为 191–209 万地址/秒，明显低于相应同步路径的约 296–303 万，因此未进入正式路径。这里的短测用于淘汰候选，不作为稳定提速结论。算术修改后的组合也重新筛选了 32/64/128/256，并未改善结果；正式算术未改变。

缓冲区和加法实验的五轮对照本身波动 5.88%；前三轮加法一度达到 3% 门槛，扩测后收益消失。保留全部原始结果，不按单次峰值选配置。检查时存在 WindowServer 和应用后台活动；未停止用户进程，也未证明波动的唯一原因。后续线程组/流水线组稳定，但不同组的绝对吞吐仍不宜直接当作同条件差值。

实现、整数边界证明和取消/所有权约定见 [设计说明](gpu-optimization-design.md)。实验开关只供测试构建使用。正式路径保留原来的模加、平方、缓冲区逐项访问和固定窗口策略；本轮有效优化来自 CPU 准备与 GPU 执行重叠，不是内核算术提速。

### 最终 GPU 配对结果与默认值

三档均为三轮、每轮至少 30 秒，计时观察器关闭。每档三轮均优于同批次的容量扩展基线。

| Batch | 优化前地址/秒 | 优化后地址/秒 | 同批次变化 | 优化后停止收尾中位数 | 初始化中位数 |
|---:|---:|---:|---:|---:|---:|
| 65,536 | 2,931,399 | 3,456,217 | +17.90% | 24.01 ms | 66.81 ms |
| 131,072 | 3,046,795 | 3,641,800 | +19.53% | 16.32 ms | 58.58 ms |
| 262,144 | 3,107,262 | 3,723,439 | +19.83% | 55.94 ms | 62.02 ms |

最终默认 **262144**，正式上限 **262144**。131072 的中位吞吐比最高值低 **2.19%**，超过预定的 2% 选择阈值；65536 低约 7.18%。因此选择 262144，而不是运行时自动跑基准。默认值和上限均为静态常量。

三档候选的吞吐波动分别为 1.62% / 0.48% / 0.50%，无需追加到五轮。停止收尾最大观测值分别为 32.01 / 16.68 / 59.69ms；它包含线程退出、在途工作及最后一次快照保存，不是 GPU 执行时间或最坏情况保证。停止时刻在批次中的位置不同，会影响这些数值，不能简单按批大小线性外推。

同一轮中，基线从 65536 扩至 262144 本身也有吞吐收益。表格只按相同 batch 计算 17.90% / 19.53% / 19.83% 的优化增益，不把扩大批次的收益算进流水线或内核优化。
